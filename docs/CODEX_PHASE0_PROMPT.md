# Codex 阶段 0：架构细化与需求检查

请在本地克隆的 FOMS 仓库中执行本阶段任务。你是本项目的产品技术架构师和全栈技术负责人。

## 一、开始前必须做的检查

1. 阅读根目录 `AGENTS.md`、`README.md`、`docs/FOMS_PRD_v1.0.md`、`docs/DEVELOPMENT_PLAN.md`、`docs/ARCHITECTURE_TODO.md` 和 `docs/SECURITY.md`。
2. 执行并记录 `git status --short --branch`，确认工作区状态。
3. 确认当前分支和远程仓库。不要丢弃、覆盖或重置任何已有本地修改。
4. 如果当前在 `main`，建议新建并切换到 `docs/phase-0-architecture` 分支；如果该分支已存在，先检查其状态，不得强制覆盖。
5. 当前仓库是 Public。所有示例必须使用虚构数据，不得加入公司真实客户、运单、员工、报价或凭据。

## 二、本阶段目标

只完成需求澄清和架构设计，不开发业务功能。

必须以 `docs/FOMS_PRD_v1.0.md` 为业务基线。可以指出其中的矛盾、缺漏和风险，但不得静默改变已经确认的业务决策。

已确认且不得擅自更改的规则：
- 首期部门为业务部，数据模型需支持未来扩展部门。
- 普通员工只能查看本人提交的问题、运营数据和导入记录。
- 部门负责人和运营管理员按授权查看部门数据。
- 公司管理层只读查看已发布的部门报告。
- 系统管理员不因系统管理角色自动获得业务数据读取权限。
- 支持网页填写、标准 Excel 模板导入、非标准 Excel 字段映射导入。
- 非标准 Excel 字段映射必须由用户确认后才能正式入库。
- AI 使用经公司批准的云端模型，调用前必须执行数据最小化和脱敏。
- 统计数字由数据库/后端计算，AI 只做解释、归纳和建议。
- AI 不得修改正式业务数据，也不得把推测写成已确认根因。
- 报告保存生成时的统计快照；公司管理层只可读取已发布报告。
- 统计时区 Asia/Shanghai。
- 部署供应商和生产环境尚未确定，架构应可迁移，不得假定已有服务器或云账号。

## 三、必须完成的架构设计

### 3.1 系统边界与组件架构
说明浏览器前端、API 后端、PostgreSQL、对象存储、异步任务、AI provider、报告导出和身份权限之间的职责与数据流。
明确哪些功能属于 v1.0，哪些属于后续版本。
提供 Mermaid 架构图和关键数据流图。

### 3.2 用户、角色、权限与数据范围
提供角色-权限矩阵及具体授权规则。
明确：
- self、department、all 的定义和继承规则。
- 多角色用户的权限合并策略。
- 系统管理员与业务数据读取权限的分离。
- 公司管理层读取已发布报告的范围。
- 报告导出、附件下载、搜索、统计 API 是否执行相同的数据权限。
- 员工离职、禁用、跨部门调动后历史数据的访问规则（作为待确认项提出建议）。
必须用具体 API 场景说明如何防止 IDOR / 越权访问。

### 3.3 数据库与 ER 设计
给出：
- ER 图（Mermaid）。
- 每张表的字段、类型、可空性、默认值、主外键、唯一约束、索引和用途。
- 关系基数。
- 软删除/停用策略。
- 审计字段。
- 迁移和数据保留策略。

重点评估并明确：
- 问题主表、分派、状态历史、评论、解决记录如何关联。
- 指标采用长表、宽表或事实表的理由。
- 指标数据的唯一业务键如何设计。
- 同日、同渠道、同业务类型的多次合法上报如何区分。
- 同一来源数据重复导入如何幂等。
- 更正、冲销、重新导入如何保留历史。
- 金额币种、重量单位、体积单位如何表达。
- 票数、件数、重量、体积各自分子分母口径如何定义。
- 统计快照和历史报告如何保证可复现。
不得只罗列表名，必须给出可以实施的字段级设计。

### 3.4 问题状态机
提供状态转换图和转换权限表。
说明哪些角色可以提交、退回补充、审核、分派、处理中、解决、关闭、重新打开。
明确状态变更与审计日志的事务边界。
说明问题编辑、补充材料和解决结果如何避免无痕覆盖。

### 3.5 Excel 双模式导入
分别设计标准模板与非标准 Excel 的端到端流程。
覆盖：
- 文件校验、工作表选择、表头行识别。
- 字段别名和映射规则。
- 单位和枚举值映射。
- 日期、数字、币种、空值处理。
- 自动映射置信度和歧义处理。
- 用户预览与确认。
- 错误行下载和修正重试。
- 重复数据识别与人工处理。
- 批次幂等、撤销/更正策略。
- 原文件、原始行和标准化结果的保留。
- 恶意文件、公式、超大文件、宏文件和解析资源限制。
不得把仅仅列名相似的字段自动映射成相同业务指标。AI 字段建议只能作为可选辅助，不能绕过人工确认。

### 3.6 AI 与数据安全
设计 AI provider adapter、调用队列、超时、重试、限流、结构化输出校验和人工审核。
列出默认禁止发送的敏感字段和允许发送的最小字段。
说明脱敏在何处执行、日志如何避免记录敏感原文、AI 返回内容如何防止 prompt injection。
说明公司尚未选定模型供应商时如何保持可替换。
AI 不直接访问数据库，不拥有修改原始业务记录的工具或权限。

### 3.7 报告与统计
定义日报、周报、月报周期边界、周起始日、截止时间和时区。
设计统计快照、报告版本、草稿、审核、发布和撤回流程。
明确普通员工、部门负责人、运营管理员、公司管理层的读取与操作权限。
说明指标口径、缺失数据、零分母、跨币种汇总和历史数据更正如何呈现。

### 3.8 API 设计
提供按模块分类的 API 清单，至少包含：
- Auth / Users / Roles / Departments
- Issues / Assignments / Comments / Resolutions
- Dictionaries / Channels / BusinessTypes / Stages
- Metrics / ManualEntry
- ImportTemplates / ImportBatches / MappingProfiles / ImportRows
- Dashboard / Statistics
- AIJobs / Reports / Exports
- Attachments / AuditLogs

每个 API 标注 HTTP 方法、路径、角色权限、数据范围、请求/响应关键字段、分页筛选、错误码和幂等要求。
无需编写业务代码。

### 3.9 部署、运维与安全
提供本地开发、测试和生产环境建议。
明确 Docker Compose 服务边界、环境变量、密钥管理、HTTPS、数据库迁移、备份、恢复、日志、监控和健康检查。
由于部署方式未确定，提供公司内网服务器与合规云服务器两种部署选项及决策条件。
不要创建真实密钥或写入生产配置。

### 3.10 测试策略与风险
提供单元测试、集成测试、权限负向测试、Excel 测试矩阵、AI mock 测试、报告快照测试、备份恢复测试和并发测试策略。
列出高风险问题、依赖条件和必须由用户确认的业务问题。

## 五、质量要求

- 文档之间的表名、字段名、角色名、状态名和 API 命名必须一致。
- 所有核心表必须有字段级定义，不接受只有概念性 ER 图。
- 每条关键权限规则必须对应到后端 API 和测试用例。
- 所有统计指标必须写明单位、分子、分母、聚合方式和缺失值处理。
- 所有不确定事项必须进入待确认清单，列出推荐选项、替代选项和影响。
- 不得自行选择未经公司批准的 AI 供应商或部署平台。
- 不得新增不在范围内的业务模块。
- 不得生成前后端业务代码、数据库迁移、安装依赖或启动服务。
